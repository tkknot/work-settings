# 文書クロスラウンドレビュー（codex × 観点別サブエージェント）

要件定義書・仕様書・設計書・議事録・Backlog 記事といった**非コードの文書**に対し、OpenAI Codex と Claude の観点別サブエージェントを交互にぶつけ、片方が見落とした指摘をもう片方が拾う反復レビューを行うガイドです。

コード差分が対象の場合は `review--cross-review`（`pr-review-toolkit` を使う版）を使ってください。本スキルは `pr-review-toolkit` を**使いません**。同プラグインのエージェントはコード前提のため、文書に当てても空振りするからです。代わりに Agent ツールで汎用エージェントを観点ごとに起動します。

**重量級ワークフロー**: 1ラウンドあたり codex 1回 + サブエージェント最大6体を消費します。ラウンド数がそのまま費用に比例するため、ラウンド数は固定値ではなく**対象文書の規模とリスクから Step 3 で算出し、実行前にユーザーの承認を取る**（ラウンド数に上限は設けず、コストの歯止めはこの承認が担う）。短いメモや一度読めば十分な文書には単発の観点別レビューで足り、Step 3 の判定が「0 ラウンド」になった場合はそちらへ誘導して終了します。

## 人間 / AI 役割分担

| 役割 | 担当 |
|------|------|
| **ラウンド数の承認**: AI が提案したラウンド数をそのまま採るか、増減するか、単発レビューに切り替えるか | 人間 |
| **書き手の意図に踏み込む書き換えの承認**: 主張・結論・スコープそのものを変える修正の採否 | 人間 |
| **タイブレークの最終判断**: codex と観点別エージェントの指摘が対立し、規約でも決着しない場合の採否 | 人間 |
| **見送りリストの採否**: Suggestion や推敲エージェントの提案を採用するか | 人間 |
| **`codex login` の実施**: 未ログイン環境でのセットアップ | 人間 |
| **ラウンド数の提案**: 文書の規模とリスクからラウンド数を算出し、根拠付きで提示する | AI |
| **レビューの実行と本文の修正**: codex・観点別エージェントを起動し、Critical/Important を反映する | AI |
| **収束判定**: seen-set・承認されたラウンド上限に基づきループを継続/終了する | AI |
| **見送りリストの整理**: 見送り理由・エスカレーション理由を記録する | AI |

## 実行手順

### Step 1: プリフライト（ゲート）

```bash
command -v codex >/dev/null 2>&1 && echo "codex: installed" || echo "codex: missing"
codex login status 2>&1
```

- `codex` が存在しない、または `codex login status` の**出力テキストに `Not logged in` が含まれる** → 中断し、`codex login` の実行を案内して終了する。
  - 終了コードでの判定はしない。未ログイン時の終了コードは未確認のため、出力テキストでの判定の方が頑健。
- **Claude のサブエージェントだけで回すフォールバックは用意しない。** 単一エンジンのレビューはクロスレビューではなく、本スキルの価値（独立した2エンジンの突き合わせ）が失われる。codex が使えないなら、観点別の単発レビューとして実施するかをユーザーに確認する。

### Step 2: レビュー対象の固定

対象文書のパス集合を開始時に1回固定し、以降のラウンドでは増やさない（レビュー中に対象が増えると収束しない）。

```bash
# 例: 対象を配列で固定する
TARGETS=("docs/requirements.md" "docs/spec.md")
```

対象は git 管理下とは限らない（Backlog の下書き・スクラッチファイルなど）ため、コード版のような `BASE` コミットの固定はしない。代わりにベースライン記録用のスナップショットをスクラッチパッドへ**1回だけ**コピーする。

```bash
SNAP="<スクラッチパッドのパス>/doc-cross-review-baseline"   # セッションのスクラッチパッド配下に置く
mkdir -p "$SNAP"
for f in "${TARGETS[@]}"; do cp "$f" "$SNAP/$(echo "$f" | tr / _)"; done
```

**毎ラウンドのレビュー対象は常に現在のファイルであり、スナップショットではない。** スナップショットは最終レポートで「開始時からどう変わったか」を示すためだけに使う。古い版を読み続けると、直した指摘が毎ラウンド再燃して収束しない（コード版が2ドット diff で回避しているのと同じ罠）。

見送りリスト・seen-set（fixed/declined の2集合）・ラウンドカウンタを初期化する。

### Step 3: ラウンド数の決定とユーザー承認（ゲート）

ラウンド数は固定しない。Step 2 で固定した対象から機械的に測れる指標でスコアを出し、**実行前に必ずユーザーの承認を取る**。

> スキル引数でラウンド数が明示されている場合（例: `/review--doc-cross-review docs/spec.md 2`）は、このスコアリングをスキップして**引数の値をそのまま使う**。ユーザーが既に意思表示しているため承認プロンプトも出さない。ヒューリスティックより明示指定が常に優先する。

**1. 指標を測る**

```bash
wc -m "${TARGETS[@]}"                      # 総文字数
grep -c '^#\{1,6\} ' "${TARGETS[@]}"       # 見出し（セクション）数
echo "${#TARGETS[@]}"                      # 対象ファイル数
```

**2. スコアを出す**

| 指標 | 条件 → 点 |
|---|---|
| 総文字数 | 2000未満 → 0 ／ 2000〜7999 → 1 ／ 8000以上 → 2 |
| 見出し（セクション）数 | 5未満 → 0 ／ 5〜14 → 1 ／ 15以上 → 2 |
| 対象ファイル数 | 1 → 0 ／ 2〜3 → 1 ／ 4以上 → 2 |
| リスクシグナル（該当ごとに +1） | 意思決定・承認を伴う（要件確定・技術選定） ／ 社外・顧客向けに公開される ／ セキュリティ・個人情報・法務・料金に言及 ／ 数値・日付・固有名詞の断定を含む ／ 既存文書との整合が必要（参照先がある） |

**3. スコアをラウンド数に変換する**

2点ごとに1ラウンド増える。**ラウンド数に上限は設けない**（スコアが伸びればそのまま提案値も伸びる）。

| 合計スコア | ラウンド数 |
|---|---|
| 0〜1 | **0**（本スキルは使わない） |
| 2〜3 | 1 |
| 4〜5 | 2 |
| 6〜7 | 3 |
| 8〜9 | 4 |
| 10以上 | 5 以上（以降も 2点ごとに +1） |

- 上限を設けない代わりに、コストの歯止めは次項「4. 承認を取る」のユーザー承認が担う。ラウンド数に比例して codex 実行回数とサブエージェント数が線形に増えるため、承認時の想定コスト提示は必須（省略不可）。
- **0 ラウンドの場合**: 文書が小さすぎてこの重量級ワークフローは割に合わない。Step 4 Phase B の観点別レビューを1回だけ回す案を提示し、「それでも反復するか」をユーザーに確認する。承認されなければここで終了する。

**4. 承認を取る**

`AskUserQuestion` で以下を提示する。**算出したラウンド数だけでなく、その根拠（各指標の実測値とスコア内訳・想定コスト）も必ず示す**。ユーザーがコストと精度のトレードオフを判断できない提示は不可。

```
提案: 2 ラウンド
根拠: 総文字数 6,400 字 (+1) / 見出し 11 個 (+1) / 対象 1 ファイル (+0) / 要件確定を伴う (+1) / 数値・日付の断定あり (+1) = 4 点
想定コスト: codex 2 回 + サブエージェント最大 10 体
```

選択肢は「提案どおり」「1 ラウンド増やす」「1 ラウンド減らす（0 なら単発レビューに切替）」「中止」を用意する。ユーザーが選んだ値を**そのラウンドの上限として確定**し、以降 Step 5 の終了判定はこの値を使う。

承認が取れて初めて Step 4 に進む。

### Step 4: 1ラウンドの実行

**Phase A — codex レビュー**

プロンプトはスクラッチパッドにファイルとして書き出し、stdin 経由で渡す（長い日本語プロンプトを引数にするとクォートが崩れる）。

```bash
codex exec -s read-only -C "$PWD" -o "$OUT/codex-round-N.md" - < "$OUT/codex-prompt-N.md"
```

- `-s read-only` を必ず指定する。codex にファイルを書かせない（修正の適用者は Claude のみ）。
- codex は `CLAUDE.md` を読まない（読むのは `AGENTS.md`）。プロンプトには **`CLAUDE.md` と `.claude/rules/*.md` の内容をインラインで埋め込む**か明示的にパスを渡し、規約違反の空振り指摘を減らす。
- レビュー対象は Step 2 で固定した `TARGETS` の**現在の内容**に限定する。プロンプトに全文を埋め込むか、パスを渡して読ませる。
- 出力フォーマットを固定で指示する（後続の重複排除・終了判定を機械的に行うため）:

  ```
  ### [Critical|Important|Suggestion] <file>:<セクション見出し または 行>
  - 指摘: <一文>
  - 根拠: <なぜ問題か>
  - 提案: <どう直すか>
  ```

**Phase A' — 反映**

Critical / Important のみ Claude が本文を修正する。Suggestion は見送りリストへ（この時点では修正しない）。主張・結論・スコープそのものを変える修正は、Critical であっても**適用前に人間の承認を取る**（書き手の意図に属する領域のため）。

**Phase B — 観点別サブエージェント**

`pr-review-toolkit` は使わない。Agent ツールで汎用エージェント（`general-purpose`）を観点ごとに起動する。文書の内容に応じて出し分け、並列起動してよい。

| 条件 | 観点 |
|---|---|
| 常時 | **論理整合性** — 矛盾・循環参照・前提条件の不整合 |
| 常時 | **網羅性** — 異常系・権限差異・端末差異・移行・運用の抜け漏れ |
| 数値・日付・固有名詞・引用を含む | **事実確認** — 本文の主張と参照先（既存文書・コード・Backlog）の突き合わせ |
| 社外・他チーム向け | **読み手適合** — 用語の統一・粒度・前提知識のギャップ |
| 実装／運用を伴う | **実現可能性** — 技術制約・コスト・スケジュール |
| 最終ラウンドのみ | **推敲** — 冗長・重複の整理（**報告のみ・自動適用しない**） |

この観点セットは `spec--requirements-workflow` Step 4 の4観点（論理整合性 / 網羅性 / 業界標準との照合 / 実現可能性）を土台に、文書レビュー向けへ「事実確認」「読み手適合」「推敲」を足したもの。要件定義の文脈では両者を対応付けて読める。

各エージェントには対象ファイルのパス・観点・Phase A と同じ出力フォーマットを明示し、**ファイルの書き換えはさせない**（単一ライター原則: 書き手は Claude 本体のみ）。ユーザーがこのスキルを起動したこと自体が、上記サブエージェントを起動する許可とみなす。

推敲エージェントの提案は、最後の変更が誰にもレビューされない状態を避けるため自動適用せず、見送りリストに載せて人間の判断に委ねる。

**Phase B' — 反映**

同様に Critical / Important のみ Claude が修正する。

### Step 5: 収束判定

各ラウンドの終わりに以下を行う。

1. **重大度フロア**: ループ継続の判定材料は Critical / Important のみ。Suggestion はカウントに入れない。
2. **seen-set は2種類に分ける**（同一集合にしない）:

   | 種別 | 次ラウンドでの扱い |
   |---|---|
   | 見送り (declined) | 恒久的に抑制。二度と再掲しない |
   | 修正済み (fixed) | 再掲を許可する。**2度目の再掲で修正を諦め**、理由付きで見送りリストにエスカレーションする |

   直した指摘が再掲されるのは「修正が不完全だった」という有効なシグナル。fixed と declined を混ぜて抑制すると、実際には問題が残ったまま「指摘なし」と偽の収束報告をしてしまう。
3. **オシレーション対策**: codex と観点別エージェントの指摘が矛盾する場合（例: 「詳細を足せ」vs「冗長だ」）、①プロジェクトの `CLAUDE.md` / `.claude/rules/*.md` に合致する方を採用する。②それでも決着しなければ本文は変更せず、見送りリストに載せて人間の判断を仰ぐ。
4. **文体・表現の好みの対立は原文を勝たせる**: 文書レビューではコードと違い、規約で決着しない「好み」の指摘が出やすい。意味が変わらない言い換えの指摘は**原文（書き手の意図）を既定**とし、修正せず見送りリストへ回す。
5. **終了条件**（いずれかを満たしたら Step 6 へ）:
   - そのラウンドで新規の Critical / Important がゼロだった（収束）
   - ラウンド数が **Step 3 で承認された上限**に達した（打ち切り）

達していなければ Step 4 に戻る。上限で打ち切る際、新規の Critical / Important がまだ出続けている場合は、Step 6 の報告でその旨を明示し、追加ラウンドの要否をユーザーに委ねる（勝手に上限を延長しない）。

### Step 6: 出力

以下を含む最終レポートを提示する。

- Step 3 で決定したラウンド数とその根拠（スコア内訳・ユーザーが増減した場合はその旨）
- ラウンドごとの指摘数推移（Critical / Important / Suggestion）
- 修正した指摘の一覧（file:セクション 付き）
- Step 2 のスナップショットと現在版の差分サマリ（何がどう変わったか）
- 見送りリスト（Suggestion・タイブレーク未決・好みの対立・推敲提案・fixed の2回目再掲エスカレーションを理由付きで列挙）
- 収束して終わったか、上限で打ち切ったか

## 重要な制約

- codex コマンドのフラグは `review--cross-review` で存在を確認済みのものに限定する（`-s`/`-C`/`-o`/`--json`/`--output-schema`/`-m`/`--skip-git-repo-check`）。モデルは `-m` で固定せずデフォルトに任せる。
- `codex apply` は使わない。修正の書き手は常に Claude のみ（単一ライター原則）。
- レビュー対象を途中で追加しない。追加したい場合はレビューを終了し、新しい対象集合で回し直す。
