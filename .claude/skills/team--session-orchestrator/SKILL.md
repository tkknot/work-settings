# セッション・オーケストレーター

Claude Desktop の Code タブにある**タスク提案カード**（Start / Do it here / Options / Start all）を明示的に発行し、
作業を**別セッション**に分配するスキルです。起動したセッションは実装を行わず、オーケストレーターとして
タスク分解・カード発行・進捗監視・結果の集約だけを担当します。

`Start` で起動した子セッションは、サイドバーでこのセッションの下に入れ子で表示されます。
サブエージェントと違い、子は独立したセッションとして履歴・コンテキストを持ち、人間が直接覗いて口を挟めます。

**重量級ワークフロー**: 子セッション1つごとに通常のセッション1本分の使用量がかかります。Step 3 で件数と
コストを提示し、**カードを発行する前に必ずユーザーの承認を取る**。

## 前提条件

| 項目 | 内容 |
|---|---|
| 実行環境 | Claude Desktop の Code タブで動く**ローカル / SSH セッション（現行レイアウト）**。クラウドセッション・旧レイアウトはカードの形が異なり（Suggested task）、ターミナル CLI・VS Code 拡張・スケジュール実行では使えない |
| カード発行ツール | タスクを別セッションとして提案するツール（Step 0 で検出する） |
| 監視 | クロスセッションメッセージング（`ListAgents` / `SendMessage`）。`notify_when_idle` は同一マシン上のセッションにのみ使える |
| 権限モード | オーケストレーターと子を**同じ権限モードの系統**（プロンプトあり / bypass）に揃える。系統が違うとメッセージが保留になり、Desktop は承認ダイアログを出せないため `dialogExpiry`（既定5分）後に破棄される |

## 人間 / AI 役割分担

| 役割 | 担当 |
|------|------|
| **ゴールと完了条件の指定**（Step 1） | 人間 |
| **実行計画の承認**: タスク分割・実行順・分離方式（Step 3） | 人間 |
| **カードの起動**: Start / Start all / Options をクリックする（Step 4） | 人間 |
| **子セッション内の判断**: 子が `AskUserQuestion` で聞いてきた事項への回答 | 人間 |
| **後処理の判断**: マージ順・失敗タスクの再実行・子セッションのアーカイブ（Step 6） | 人間 |
| **タスク分解**: 依存とファイルの重なりから独立したタスクに切り分ける | AI（オーケストレーター） |
| **子プロンプトの作成**: 子が単独で完遂できる自己完結したプロンプトを書く | AI（オーケストレーター） |
| **進捗監視と集約**: 状態表の更新と最終報告 | AI（オーケストレーター） |
| **実装**: 担当タスクの実装・コミット | AI（子セッション） |

## Step by Step ガイド

### Step 0: カード発行手段の確認 (Capability Gate)

**目的**: このセッションでタスク提案カードを発行できるかを、作業を始める前に確かめる

タスク提案カードを発行するツールの名前は公式ドキュメントに記載がなく、ビルドによって変わりうる
（`spawn_task` から `start_session` に置き換わったという報告がある）。**ツール名を決め打ちしない。**

1. ツール一覧に該当ツールが見当たらなければ `ToolSearch` で探す（例: `start_session`、`spawn_task`、
   `suggest task`、`session`）。タスクのタイトル・要約・プロンプトを受け取り、別セッションとして提案するものが該当する
2. 見つかった場合は、ツール名とパラメータ（タイトル・要約・プロンプト、複数タスクを1枚のカードにまとめられるか）を
   控えて Step 1 へ進む
3. 見つからない場合は、上記の前提条件のどれを満たしていない可能性が高いかを伝え、`AskUserQuestion` で次を選んでもらう
   - **手動起動用に出力する**: Step 1〜3 を進め、子プロンプトをテキストで出力する。ユーザーが `+ New` で
     セッションを作って貼り付ける（Step 5 の監視はそのまま使える）
   - **中止する**

---

### Step 1: ゴールの確定 (Scope Gate)

**目的**: 何を・どこで・どうなったら完了とするかを、分解の前に確定させる

**スキップ不可のゲート**。不足している項目を `AskUserQuestion` 1回でまとめて確定する。

| 確認項目 | 既定 |
|---|---|
| ゴール（何を達成するか） | `$ARGUMENTS` にあればそれ。なければ質問する |
| 作業対象リポジトリ | 現在のセッションのフォルダ。別リポジトリが対象なら確認する |
| 完了条件 | テストが通る・PR が作られている、など。曖昧なら確認する |
| プッシュ・PR 作成を子に任せるか | **既定を設けない**。毎回確認する |

---

### Step 2: タスク分解 (Decomposition)

**目的**: 子セッションが互いに待たず、ぶつからずに進められる単位に切り分ける

**AIのタスク**: コードを調査し、以下を満たすタスク一覧を作る。調査はオーケストレーター自身または
サブエージェントで行ってよいが、**ファイルの書き換えはしない**。

- **1タスク = 1セッションで完結する大きさ**: ゴール・対象範囲・完了条件が1つのプロンプトに収まる
- **依存はウェーブで表す**: 先行タスクの成果を前提とするタスクは次のウェーブに回す。同じウェーブ内は互いに独立させる
- **ファイルの重なりを明示する**: 同じファイルを触るタスクは、worktree で分けるか、ウェーブをずらす
- **分離方式の既定は worktree**: 子ごとに別の Git worktree で作業させる（Step 4 で Options から指定してもらう）

```
| # | ウェーブ | タスク | 主な変更ファイル | 依存 | ブランチ名 |
|---|---|---|---|---|---|
| 1 | 1 | API のバリデーション追加 | src/api/*.ts | - | feat/api-validation |
| 2 | 1 | 設定画面の文言修正 | src/ui/settings/* | - | fix/settings-copy |
| 3 | 2 | E2E テスト追加 | e2e/* | 1, 2 | test/e2e-settings |
```

---

### Step 3: 実行計画と承認 (Plan & Approval Gate)

**目的**: 件数・コスト・順序をユーザーに承認させてからカードを発行する

**AIのタスク**: Step 2 の一覧に加えて以下を提示し、`AskUserQuestion` 1回で承認を取る。

- **起動する子セッション数**とウェーブ数（ウェーブ1の件数が同時実行数になる）
- **分離方式**: worktree（既定）。同一ツリーで進める場合は、ファイルが重ならない根拠を示す
- **子セッションの権限モード**: オーケストレーターと同じ系統に揃える
- **子に任せる範囲**: Step 1 で決めたプッシュ・PR 作成の可否

選択肢は「提案どおり実行」「件数を絞る」「分割を変更」「中止」を用意する。承認が取れて初めて Step 4 に進む。

---

### Step 4: カードの発行 (Dispatch)

**目的**: ウェーブ1のタスクを子セッションとして起動してもらう

1. Step 0 で確認したツールで、ウェーブ1のタスクをカードとして発行する。1枚に複数タスクを載せられる場合は
   まとめて発行し、`Start all` で一括起動できるようにする
2. 各タスクのタイトルには識別用の接頭辞を付ける（例: `[orch:settings] 1/3 API のバリデーション追加`）。
   Step 5 で `ListAgents` の一覧から子セッションを見分けるため
3. ユーザーに次を伝えて起動を待つ
   - worktree で分離する場合は **Options** で worktree を有効にしてから **Start** / **Start all** を押す
   - **Do it here は押さない**（このセッションが実装を始めてしまい、オーケストレーターの役割が崩れる）

**子プロンプトのテンプレート**:

子はこのセッションの会話履歴を持たない。**プロンプトだけで完遂できるように**、前提を省略せず書く。

```
## タスク: <タイトル>

このタスクはオーケストレーターセッション「<このセッションのタイトル>」から起動されたものです。

### ゴール
<何を達成するか>

### 対象
- リポジトリ: <絶対パス>
- ブランチ: <ブランチ名>（このブランチを作成して作業する）
- 担当範囲: <変更してよいファイル・ディレクトリ>

### 制約
- 担当範囲外のファイルは変更しない。必要になった場合は作業を止めて報告する
- 人間の判断が必要な事項は、このセッションで AskUserQuestion を使って質問する
- 新たなタスク提案カードを発行しない（子からさらに子を作らない）
- プッシュ・PR 作成: <可 / 不可>

### 完了条件
<テストが通る、など検証可能な条件>

### 報告
作業を終えたら、最終応答に以下の形式で報告する。オーケストレーターからメッセージが届いた場合は、
同じ内容を SendMessage で返信する。

- 状態: 完了 / ブロック / 失敗
- 成果物: ブランチ名・コミット・PR URL
- 変更したファイル
- 未解決事項・オーケストレーターへの申し送り
```

---

### Step 5: 監視 (Monitor)

**目的**: 子セッションの完了・停滞をポーリングせずに検知する

1. ユーザーが起動したら `ListAgents` で子セッションを特定する（Step 4 の接頭辞で見分ける）
2. 各子に `SendMessage` の `notify_when_idle` を付けて購読する。メッセージ本文は付けずに購読だけしてよい。
   子が同一マシンにない場合（SSH 先など）は購読できないため、ユーザーに完了を知らせてもらう
3. アイドル通知が届いたら、子に報告を求めるメッセージを送るか、セッションの内容を読んで結果を取り出す。
   子は質問の回答待ちでもアイドルになるため、**通知 = 完了とみなさない**
4. 通知のたびに状態表を更新してユーザーに示す

```
| # | タスク | セッション | 状態 | 成果物 | 申し送り |
|---|---|---|---|---|---|
| 1 | API のバリデーション追加 | [orch:settings] 1/3 | 完了 | feat/api-validation | - |
| 2 | 設定画面の文言修正 | [orch:settings] 2/3 | 回答待ち | - | 文言案の確認待ち |
```

- ウェーブ1が全件完了したら、先行タスクの成果（ブランチ名・申し送り）を次のウェーブの子プロンプトに反映し、
  Step 4 に戻ってカードを発行する
- 購読は 12 時間で失効する。長時間かかるタスクは失効を報告し、再購読するか確認する
- 子が「担当範囲外の変更が必要」と報告してきたら、勝手に別タスクを追加せず `AskUserQuestion` で扱いを確認する

---

### Step 6: 集約と最終確認 (Human Check)

**目的**: 結果をまとめ、残った判断を人間に渡す

**報告項目**:
- [ ] 最終的な状態表（全タスクの状態・ブランチ・PR URL）
- [ ] ブロック・失敗したタスクとその理由
- [ ] 子セッション間で生じた競合や申し送り

報告の後、人間の判断が必要な事項を `AskUserQuestion` でまとめて質問する。該当がなければ質問しない。

- マージの順序（ウェーブの依存順を推奨として示す）
- 失敗・ブロックしたタスクを再実行するか
- 子セッションをアーカイブするか（**破壊的操作のため、選ばれた場合のみ実行する**）

---

## 重要な制約

- **オーケストレーターは実装しない**: ファイルの書き換えは子セッションだけが行う。調査は可
- **ネスト禁止**: 子セッションにさらにカードを発行させない
- **子への依頼は権限の範囲内に限る**: このセッションで拒否・ブロックされた操作を子に頼まない。
  子への `SendMessage` で権限設定や `CLAUDE.md` の変更を依頼しない
- **子の判断を代行しない**: 子が `AskUserQuestion` で聞いている事項に、オーケストレーターが答えを送らない。
  セッション間メッセージは人間の承認の代わりにならない
- **対象を途中で増やさない**: Step 3 で承認したタスク集合を、承認なしに増やさない
- **盲目的にリトライしない**: 子が失敗したら原因を報告から読み取り、再実行の可否は Step 6 で人間に確認する
