# Backlog 小課題オーケストレーター

親課題キーを起点に、**自分が担当している未完了の小課題**を洗い出し、1件ずつ「実装 → 検証方法作成 → PR 作成」まで
運ぶオーケストレーターです。あなたはこのセッションのオーケストレーターとして、小課題の順序と進捗を管理します。

**重量級ワークフロー**: 小課題1件あたり実装・検証方法設計・PR 作成が発生します。件数がそのままコストに比例するため、
Step 3 で対象件数と想定コストを提示し、**実行前に必ずユーザーの承認を取る**。

Backlog への書き込み（ステータス更新・コメント投稿）は他人も見る場所への破壊的操作です。**既定値を設けず、
Step 5 で毎回ユーザーに確認する**。省略しない。

## 人間 / AI 役割分担

| 役割 | 担当 |
|------|------|
| **対象リポジトリの指定**: 小課題のコードがどのリポジトリにあるかを決める（Step 1・**毎回確認する**） | 人間 |
| **実行計画の承認**: 対象件数・実行順序・実行モードを承認する（Step 3） | 人間 |
| **仕様の疑義への回答**: 課題本文だけでは実装方針が決まらない場合の判断 | 人間 |
| **Backlog 書き戻しの可否**: ステータス更新・コメント投稿を行うか（Step 5・**毎回確認する**） | 人間 |
| **プッシュ・PR 作成の承認**: リモートへ反映してよいかの判断 | 人間 |
| **マージの実施**: 作成された PR のレビューとマージ | 人間 |
| **小課題の収集**: 親課題配下から自分担当の未完了課題を漏れなく列挙する | AI |
| **実行順序の提案**: 依存関係・ファイルの重なりから順序と実行モードを提案する | AI |
| **実装**: 課題ごとにブランチを切り、TDD サイクルで実装・コミットする | AI |
| **検証方法の作成**: テスト設計技法に基づく検証方法を課題ごとに作成する | AI |
| **PR 本文の作成**: 実装内容から PR テンプレートを埋める | AI |
| **進捗の集約**: 完了 / 未完了 / ブロック中を一覧で報告する | AI |

---

## 実行モード

Step 3 で選択する。**既定は逐次**。

| モード | 挙動 | 適用場面 |
|---|---|---|
| **逐次**（既定） | 1課題ずつ本体が実装する。調査・検証方法設計のみ `general-purpose` サブエージェントへ委譲する | 課題間でファイルが重なる／件数が少ない |
| **並列**（opt-in） | `git--git-worktree` で小課題ごとに worktree を分け、サブエージェントに1課題ずつ担当させる | 課題が互いに独立していて件数が多い |

並列モードは worktree による物理分離が前提。同一ワークツリーで複数課題を並行実装しない（コミットが混ざる）。

## Step by Step ガイド

### Step 1: 対象の確定 (Scope Gate)

**目的**: 何を・どのリポジトリで片付けるのかを、作業を始める前に確定させる

**スキップ不可のゲート**。以下を `AskUserQuestion` 1回でまとめて確定する。

| 確認項目 | 既定 |
|---|---|
| 親課題キー（例: `PROJ-123`） | `$ARGUMENTS` にあればそれ。なければ質問する |
| **作業対象リポジトリの絶対パス** | **既定を設けない**。cwd を対象と決め打ちしない |
| 対象ステータス | `statusId: [1, 2]`（未対応・処理中）。処理済みも含めるかを選べるようにする |

- 対象リポジトリを推測して省略しない。小課題のコードは、このスキルを起動したディレクトリとは
  別のリポジトリにあるのが普通のため。
- 指定されたパスが設定リポジトリ（`work-settings` など）だった場合は、その旨を伝えて再確認する。
- Backlog MCP ツール（`get_myself` 等）が使えない場合はここで中断し、MCP の接続を案内して終了する。
  **フォールバックは用意しない**（課題一覧を推測で作らない）。

---

### Step 2: 小課題の収集 (Subtask Collection)

**目的**: 親課題配下から自分担当の未完了課題を漏れなく列挙する

**AIのタスク**: `spec--backlog-integration` スキルの「親課題に紐づく小課題を取得する」を参照して実行する。

1. `get_myself` で自分のユーザー ID を取得
2. `get_issue` で親課題を取得し、**課題キーから数値の課題 ID と `projectId` を解決する**
   （`PROJ-123` のままでは子課題の `parentIssueId` と照合できず、結果が空になる）
3. `get_issues` で子課題を取得する。`parentIssueId` をサーバー側フィルタとして渡せるかは MCP スキーマ次第。
   **渡せない場合や結果が空の場合は、`projectId` + `assigneeId` + `statusId` で取得してから各課題の
   `parentIssueId` をクライアント側で照合する**。`projectId` を省くと全プロジェクト横断になり、
   `count` の上限で打ち切られた結果を「全件」と誤認する
4. 取得結果を一覧表で提示する。**取得件数が `count` と同数だった場合は打ち切りの可能性がある**ため、
   完全な一覧として扱わずその旨を明記する（漏れたまま「全件完了」と報告しないため）

```
| 課題キー | 件名 | ステータス | 見積 | 依存 |
|---|---|---|---|---|
| PROJ-124 | ログインAPIの追加 | 未対応 | 3h | - |
| PROJ-125 | ログイン画面の実装 | 処理中 | 5h | PROJ-124 |
```

対象が0件の場合は、使用したフィルタ条件（親課題 ID・担当者・ステータス）を明示して終了する。
「担当者が別人だった」「ステータス条件から外れていた」など、空になった理由が分かる形で報告する。

---

### Step 3: 実行計画と承認 (Plan & Approval Gate)

**目的**: 実行順序とコストをユーザーに承認させてから着手する

**AIのタスク**: 以下を提示し、`AskUserQuestion` 1回で承認を取る。

- **実行順序**: 依存のある課題を先に置く。依存が課題本文から読み取れない場合は推測せずユーザーに聞く
- **実行モード**: 上表から提案する（既定は逐次）。並列を提案する場合は課題間でファイルが重ならない根拠を示す
- **想定コスト**: 対象件数と、1件あたりに走る作業（実装・検証方法・PR）

選択肢は「提案どおり実行」「件数を絞る」「順序を変更」「中止」を用意する。承認が取れて初めて Step 4 に進む。

---

### Step 4: 小課題ごとの実行 (Per-Subtask Execution)

**目的**: 1課題を実装・検証方法・PR まで通しで完了させる

1課題につき Phase A → B → C を回し、**1課題終わるごとにユーザーへ短く報告してから次の課題へ進む**。
まとめて全件片付けてから報告しない（軌道修正の機会を潰さないため）。

**Phase A — 実装**

1. `get_issue` / `get_issue_comments`（`order: "asc"`）で課題の内容と経緯を把握する
2. 課題キーを含むブランチを切る（例: `feature/PROJ-124-login-api`）
3. `arch--design-implementation-workflow` の TDD サイクル（🔴 Red → 🟢 Green → 🔵 Refactor）で実装する
4. `.claude/rules/commit-convention.md` に従ってコミットする

課題本文だけで実装方針が決まらない場合は、仮定で進めずユーザーに確認する。

**Phase B — 検証方法の作成**

`test--verification-workflow` の Step 1〜3 を適用する。

- Step 1: 過去の類似課題を検索し、チームで定着している検証方法の書き方と過去不具合を拾う
- Step 2: テスト設計技法を選定し、CSV 形式で検証方法を作成する
- Step 3: 技術用語を業務用語へ置換する自己レビューを行う

E2E 自動化（同スキル Step 4）まで行うかは、課題の内容を見てユーザーに確認する。既定では行わない。

**Phase C — PR 作成**

`git--create-pull-request` のテンプレートに沿って PR 本文を作成する。

- 「課題へのリンク」に Backlog の課題 URL を入れる
- 「動作確認」に Phase B で作成した検証方法を要約して入れる
- プッシュ前にユーザーへ確認する。**PR 本文に AI の署名を付けない**（同スキルの制約を継承）

---

### Step 5: Backlog への書き戻し (Write-back Gate)

**目的**: Backlog 側の更新を、ユーザーの明示的な承認のもとでのみ行う

**既定値を設けない。毎回確認する。** 前回の選択やステータスの状況から推測して省略してはならない。

| 操作 | 内容 |
|---|---|
| `add_issue_comment` | PR リンク・検証方法を課題にコメントする |
| `update_issue` | ステータスを更新する（例: 処理中 → 処理済み） |
| 何もしない | Backlog を一切更新せず、報告のみで終える |

複数の小課題をまとめて更新する場合も、**対象課題と操作内容を一覧で示してから**承認を取る。
承認されなかった操作は実行せず、Step 6 の報告に「未反映」として残す。

---

### Step 6: 最終報告と人間確認 (Human Check)

**目的**: 残作業と人間の判断が必要な事項を明示して引き継ぐ

**報告項目**:
- [ ] 完了した小課題（課題キー・ブランチ名・PR URL・Backlog 更新の有無）
- [ ] 未完了・ブロック中の小課題とその理由
- [ ] Step 5 で承認されず未反映のままの Backlog 更新
- [ ] 人間の判断が必要な事項（マージ可否・仕様の疑義・見送った課題）

---

## 重要な制約

- **ファイル競合を避ける**: 並列モードでは worktree で物理分離する。逐次モードでは書き手を本体のみに限定し、
  サブエージェントには調査・設計をさせて実装させない
- **ネスト禁止**: サブエージェントがさらにチームを作らない
- **Backlog への書き込みは Step 5 のゲートを通ったものだけ**。調査の過程で `update_issue` を呼ばない
- **対象を途中で追加しない**: Step 2 で固定した課題集合を実行中に増やさない。増やす場合は一度終了して回し直す
- **盲目的にリトライしない**: 想定外のエラーや実装の行き詰まりが出たら、リトライを繰り返さず立ち止まって
  ユーザーへ相談する
