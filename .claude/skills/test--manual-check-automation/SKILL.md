# 手動確認の自動テスト化

人間がブラウザや端末で毎回手で叩いている確認作業を洗い出し、**費用対効果の高い順に自動テストへ置き換えて、手動の打鍵を限りなくゼロに近づける**スキルです。

大原則は次の3つです。どれも省略・緩和しないこと。

1. **実装は直さない**: 変更してよいのはテスト側だけ（後述の書き込み許可リスト）。最後に機械的なゲートで確認する。
2. **コスパ重視**: 「削減できる打鍵 × 実行頻度 ÷ 作成・保守コスト」の高い順に着手し、手動確認をカバーできる**一番下の層**でテストを書く。
3. **品質は犠牲にしない**: コストを下げるためにアサーションを弱めない、不安定なテストを入れない、通すためにテストを曲げない。

## 対象の決め方

`$ARGUMENTS` で対象を受け取る。

- ファイルパス → そのファイルが担う振る舞いを対象にする
- 機能名・課題キー → 該当する実装と検証方法（Backlog の検証方法・PR 本文など）を探して対象にする
- **省略時** → 「現在のブランチ差分（デフォルトブランチとの merge-base から作業ツリーまで）を対象にしてよいか」をユーザーに確認してから進める。確認なしで決め打ちしない

対象が決まったら、作業開始前に**基準点**を記録する（Step 5 のゲートチェックで使う）。

```bash
git status --porcelain   # 未コミットの変更があれば、先にコミットするか退避するかをユーザーに確認する
START=$(git rev-parse HEAD)
```

## 人間 / AI 役割分担

| 役割 | 担当 |
|------|------|
| **自動化計画の承認**: どの手動確認を、どの層で、どこまで自動化するかを決める | 人間 |
| **グレーゾーン変更の承認**: テストランナー設定・devDependency 追加・新フレームワーク導入の可否を決める | 人間 |
| **バグ候補の扱い**: 新テストが実装のバグを見つけた場合、期待失敗マーカーで残すか別途修正するかを決める | 人間 |
| **残す手動確認の受け入れ**: 自動化しない（できない）項目をそのまま手動で残してよいか判断する | 人間 |
| **手動確認の棚卸し**: 検証方法・PR 本文・README などから手で叩いている手順を列挙する | AI |
| **ROI 評価と層の選定**: 各項目の削減打鍵・頻度・コストを見積もり、優先順位と層を提案する | AI |
| **テスト実装と実行**: 既存のフレームワーク・ヘルパーに倣ってテストを書き、実行して緑にする | AI |
| **テストの検証**: 追加したテストが「壊れたら落ちる」ことを確認する | AI |
| **ゲートチェックと報告**: 実装に触れていないことを機械的に確認し、結果を3つのリストで報告する | AI |

## 書き込み許可リスト（「実装は直さない」の定義）

| 区分 | 対象 | 扱い |
|------|------|------|
| **許可** | テストファイル（`*.test.*` / `*.spec.*` / `test_*.py` / `tests/` / `__tests__/` / `e2e/` 等）、フィクスチャ、テストデータ、テスト専用ヘルパー・モック | 自由に追加・変更してよい |
| **要承認** | テストランナー・カバレッジの設定ファイル、devDependency の追加、テストフレームワークの新規導入、CI のテストジョブ | 変更前に理由を添えてユーザーの承認を取る |
| **禁止** | 上記以外すべて（プロダクトコード、本番依存、ビルド設定、テストのためだけの export 追加や `data-testid` の付与も含む） | 触らない。必要なら「テスト容易性の課題」として報告する |

テストのパス規約はプロジェクトごとに異なる。初回に既存テストの配置を Glob で確認し、許可リストのパターンを具体化してから作業する。

## Step by Step ガイド

### Step 1: 手動確認の棚卸し (Inventory)

**目的**: 人間が今手で叩いている確認を、1項目1行で漏れなく列挙する

**AIのタスク**: 以下の情報源から手動確認の手順を拾う（独自フォーマットは作らず、元の表記をそのまま引用する）

- Backlog 課題の検証方法（`spec--backlog-integration` で取得）
- `test--verification-workflow` / `test--test-case-design` で作られたテストケース CSV
- PR 本文の「動作確認」「テスト手順」欄、README・手順書の確認手順
- 対象コードの差分から読み取れる、確認が必要なのに自動テストがない振る舞い

あわせて既存の自動テストを確認し、**すでに自動テストでカバーされている手動確認**は「重複」として印を付ける（新規に書かず、手動側を省略できると報告するだけでよい）。

---

### Step 2: ROI 評価と層の選定 (Prioritize)

**目的**: 打鍵削減の効果が大きく、安く、安定して書けるものから順に並べる

**AIのタスク**: 各項目を以下の表で評価する

| 列 | 内容 |
|------|------|
| 手動確認 | Step 1 の項目 |
| 削減打鍵 | 1回の確認で省ける操作数の目安（画面遷移・入力・目視の回数） |
| 頻度 | その確認を行う頻度（PR ごと / リリースごと / 稀） |
| 層 | 下記の選定基準で決めた層 |
| コスト | 作成＋保守の目安（小 / 中 / 大） |
| 判定 | 自動化する / 重複（既存でカバー済み） / 手動で残す（理由付き） |

**層の選定基準**: 手動確認の意図を**欠けなくカバーできる一番下の層**を選ぶ。下の層ほど速く安定し、保守コストが低い。

| 層 | 向いている確認 |
|------|------|
| ユニット | 計算・変換・バリデーション・分岐など、入出力で決まる振る舞い |
| 結合（API・DB・コンポーネント） | エンドポイントの応答、永続化、コンポーネントの表示と操作 |
| E2E | 画面をまたぐ導線、認証を含む一連のフローなど、下の層では意図が欠けるもの |

**「手動で残す」の典型**: 見た目の美しさ・使い勝手の主観評価、実機や外部サービスに依存し安定して再現できないもの、実装を変えないとテストできないもの（Step 4 の「テスト容易性の課題」へ）。

**人間のタスク**: 優先順位表を見て、自動化する範囲と要承認の変更（許可リストの「要承認」）の可否を決める。**承認を得るまで Step 3 に進まない。**

---

### Step 3: テスト実装 (Implement)

**目的**: 承認された項目を、既存の流儀に揃えて品質を落とさずに自動テスト化する

**AIのタスク**: 以下を守って実装する

- **既存資産を再利用する**: 既存のフレームワーク・ヘルパー・フィクスチャ・命名・配置に合わせる。同じ役割のヘルパーを新しく作らない
- **振る舞いをアサートする**: 手動確認で人間が見ていた結果（表示・応答・保存内容）を検証する。内部実装の呼び出し回数や private な状態には依存しない
- **品質の下限**（コスト削減の名目でも破らない）:
  - 固定時間の `sleep` / `waitForTimeout` で待たない。条件待ち（要素の出現・応答の到着）を使う
  - 実ネットワーク・現在時刻・乱数に依存しない。外部境界でのみモック・固定化する
  - 何でもスナップショットに丸投げしない。スナップショットは差分の意味を人間が読めるものに限る
  - 1テスト1意図。テスト名で「どの手動確認を置き換えたか」が分かるようにする
  - テスト間で状態を共有しない（順序依存させない）
- E2E で画面要素を特定する際は、既存のロール・ラベル・文言で特定する。`data-testid` を足したくなったら禁止区分なので「テスト容易性の課題」に回す

---

### Step 4: 実行と検証 (Verify)

**目的**: 追加したテストが緑であるだけでなく、「壊れたら落ちる」意味のあるテストであることを確かめる

**AIのタスク**:

1. **実行**: 追加したテストと関連する既存テストを実行し、すべて通ることを確認する
2. **落ちることの確認**: 各テストについて、**テスト側の期待値を一時的に誤った値に変えて**失敗することを確認し、元に戻す。実装を変異させて確かめる方法は取らない（リポジトリに既存の mutation testing ツールがある場合のみ、それを使ってよい）
3. **安定性の確認**: E2E・結合テストは複数回（目安3回）連続実行し、すべて通ることを確認する。一度でも落ちたら原因を直すまで完了扱いにしない

**新テストが実装のバグを見つけた場合**（期待どおりに書いたテストが、実装の不具合で落ちる）:

- アサーションを弱める・期待値を実装に合わせる・テストを消す、のいずれもしない
- 実装も直さない
- **その場で止めて**「バグ候補」として再現手順・期待値・実際の値を報告し、扱いを人間に委ねる（例: 課題キー付きの期待失敗マーカー `test.fails` / `xfail` で残す、`debug--bug-investigation-workflow` で別途修正する）

**テストが書けない場合**（実装に差し込み口がない、外部依存が密結合など）:

- リファクタリングしない。外部境界より内側をモックで無理やり差し替えない
- 「テスト容易性の課題」として、どこをどう変えればテストできるかを記録し、その項目は手動確認として残す

---

### Step 5: ゲートチェックと報告 (Gate & Report)

**目的**: 実装に触れていないことを機械的に保証し、手動確認がどれだけ減ったかを示す

**AIのタスク1: ゲートチェック**

```bash
# 開始時に記録した START から、コミット済み・未コミット・未追跡の変更をすべて列挙する
{ git diff --name-only "$START"; git ls-files --others --exclude-standard; } | sort -u
```

列挙されたパスが**すべて書き込み許可リストの「許可」区分、または承認済みの「要承認」区分**に入っていることを確認する。1つでも外れていれば完了とせず、その変更を取り消してから報告する。

**AIのタスク2: 報告**（チャットに出力する）

```markdown
## 自動化した手動確認
| 手動確認 | 置き換えたテスト | 層 | 削減打鍵 / 頻度 |
|---|---|---|---|

## 重複（既存テストでカバー済み）
| 手動確認 | カバーしている既存テスト |
|---|---|

## 残る手動確認
| 手動確認 | 残す理由 |
|---|---|

## テスト容易性の課題・バグ候補
| 箇所 | 内容 | 対応案 |
|---|---|---|

## 実行コマンド
<追加したテストを実行するコマンド>
```

元の検証方法（Backlog・PR 本文）に「自動テスト化済み」を反映するかは、人間に確認してから行う。
